# v1.0 production-reference release decision

This document defines the **human review decision** for the Energy Flex Trust
Platform `1.0.0` production-reference release. Exact machine identity and artifact
digests are generated by the Release Evidence workflow in `RELEASE_RECORD.json` so
the source commit is not represented by a self-referential value committed into the
same Git tree.

## Release scope

v1.0 is a compatibility and evidence freeze over the v0.9 release-candidate
architecture. It does not introduce a new live market/device transport or expand the
physical-control boundary.

The v1 release freezes:

- package/runtime/OpenAPI version `1.0.0`;
- the public `/v1` route set in `contracts/api-surface-v1.json`;
- existing idempotency semantics;
- audit/evidence integrity-sensitive formats;
- `energy-flex-dispatch.v1` plus exact v0.3 legacy queue-drain parsing;
- supported Python 3.11/3.12/3.13 and PostgreSQL 16/17 repository test paths;
- stop/drain/migrate/start deployment choreography for exact-schema migrations;
- explicit production-reference non-claims.

## Required exact-head evidence before merge

The final pull-request head must have all of the following green on the **same SHA**:

1. Main CI — Python 3.11, 3.12 and 3.13; Ruff; compile; full pytest/coverage;
   OIDC/OpenADR trust-boundary checks.
2. PostgreSQL Recovery Gate — PostgreSQL 16 and 17 migration, least-privilege role
   matrix, deterministic dump/restore integrity and rollback probe.
3. Security Gates — bounded advisory exception validation, `pip check`, runtime
   dependency audit and CodeQL security-extended analysis.
4. Release Evidence — wheel `1.0.0`, SPDX 2.3 SBOM, SHA-256 evidence, hardened
   non-root/read-only container execution and uploaded `RELEASE_RECORD.json`.

A merge approval is not valid if the PR head changes after the evidence is reviewed.
The merge operation should therefore use the exact expected head SHA.

## Required main/tag evidence

After merge to `main`, push-triggered Release Evidence must additionally complete the
GitHub provenance and SBOM attestation steps for the merged commit. A `v1.0.0` tag
must point to the approved `main` commit and must not be created from a rebuilt or
unreviewed source tree.

The generated `RELEASE_RECORD.json` records:

- release version;
- exact source commit and ref;
- workflow event;
- wheel filename and SHA-256;
- SPDX SBOM SHA-256;
- hardened local container image ID;
- reproducible build epoch.

## Residual-risk decision

`RESIDUAL_RISK.md` is the authoritative register. Every R-01 through R-15 entry has
an explicit `accepted`, `transferred` or `out_of_scope` disposition and accountable
owner role. No item is silently marked closed because CI is green.

In particular:

- live destination security, PAM-backed recovery identity, KMS/HSM checkpoint
  custody, backup RPO/RTO, gateway protections and deployment encryption are
  transferred to accountable deploying-institution roles;
- tenant isolation and OpenADR certification/conformance remain explicitly out of
  scope for the reference release;
- source dependency lockfile reproducibility, exact-schema stop/drain deployment and
  moving major-version GitHub Action/base-image references remain visible accepted
  repository-level residual risks;
- the `cryptography` R-15 exception is temporary, narrow and expires 2026-09-30.
  Introduction of the affected PKCS#7 decrypt APIs or expiry of the exception is a
  release blocker.

## Approval boundary

Repository maintainer approval of the final v1.0 pull request authorizes merging the
reviewed production-reference source only. It does **not** constitute approval for a
specific institution, electricity market, physical device, regulatory regime or
production deployment.

## Explicit non-claims

The v1.0 release does not establish:

- OpenADR certification or conformance;
- electricity-market participation or settlement acceptance;
- safe control of a physical energy asset;
- DORA, NIS2, ISO or grid-code compliance/certification;
- tenant isolation where it is not implemented;
- legal admissibility or absolute non-repudiation;
- exactly-once external physical/market effects;
- institution-specific production approval.
